# 06 — DiscoveryPlanV1 Contract

The single source of truth for the schema is
[DiscoveryPlanV1.schema.json](DiscoveryPlanV1.schema.json) (JSON Schema draft-07). This
document explains *why* it's shaped this way and the constraints that shaped it.

## Design constraints that shaped this schema

1. **No `$ref` / `$defs`.** n8n's **Structured Output Parser** sub-node (used by the Basic LLM
   Chain in MR-01/MR-02, see [08-n8n-workflows.md](08-n8n-workflows.md)) does not resolve
   `$ref` when you "Define using JSON Schema". Every object shape is therefore inlined
   directly, even though this means `id`/`label`/`description` triples are repeated across
   several array item schemas instead of being defined once. Verified in n8n's official docs
   for the Structured Output Parser node — **do not reintroduce `$ref`** even for readability;
   duplication here is a deliberate trade-off for a working structured-output contract, not an
   oversight.
2. **`additionalProperties: false` everywhere.** Forces the LLM's structured output to match
   the schema exactly — no stray fields the app doesn't know about, no silently-dropped
   validation errors.
3. **Every list item has a stable `id`.** The Discovery Plan screen renders lists the user can
   edit/toggle/remove individually ([01-product-model.md](01-product-model.md)). Without a
   stable `id`, the UI would have no reliable key for edits across re-renders, and MR-02
   couldn't reference "which item changed". `id` values only need to be unique **within their
   own array**, not globally. See "Stable IDs" below for the exact rules MR-02 (and manual
   revision) must follow.
4. **`schemaVersion` is a `const`.** Guarantees the app can immediately detect a
   contract-mismatch (e.g. old cached workflow returning an older shape) instead of silently
   accepting a document that merely happens to validate against a newer/older schema by
   coincidence.
5. **No sales/ROAS/conversion fields anywhere.** Enforces the vocabulary rule from
   [01-product-model.md](01-product-model.md) structurally, not just by convention — there is
   no field an LLM could fill in with a sales claim, because no such field exists.
6. **`discoveryStrategies[]` items are executable, not aspirational.** Each item's `source`/
   `mode` pair must correspond to a discovery capability the collector runtime actually
   supports (communicated to MR-01 as `availableDiscoveryCapabilities` in the request — see
   [07-api-contract.md](07-api-contract.md) — this is request *input*, not part of this schema).
   Only `{ source: "META_AD_LIBRARY", mode: "KEYWORD_SEARCH" }` is valid today; the enum is
   deliberately narrow so the LLM cannot propose a strategy (e.g. a hashtag/community sweep,
   web search, landing-page analysis) the pipeline has no way to execute. Extending the enum
   (`WEB_SEARCH`, `ADVERTISER_PAGE`, `LANDING_PAGE`, `SOCIAL_PUBLIC_CONTENT`, ...) is expected
   later, one at a time, each requiring a `schemaVersion` bump plus the matching collector
   capability actually landing first — never the other way around.

## Field-by-field summary

| Field | Type | Purpose |
|---|---|---|
| `schemaVersion` | `"1.1"` (const) | Contract version guard |
| `capabilityUnderstanding` | string | Model's restatement of the brief, for user confirmation |
| `marketBreadth` | object | Country/language scope + free-text notes |
| `seedQueries[]` | object[] | First search probes: `id`, `query`, `rationale`, `priority`, `enabled` (bool — off without deleting), `source` (`LLM_INITIAL \| LLM_REVISION \| USER \| DISCOVERY_EXPANSION`) |
| `candidateProductTypes[]` | object[] | Plausible formats to keep an eye out for: `id`, `label`, `description` |
| `initialTaxonomy[]` | object[] | Starter topic/segment categories: `id`, `label`, `description` |
| `discoveryStrategies[]` | object[] | Executable search strategies: `id`, `source` (`META_AD_LIBRARY`), `mode` (`KEYWORD_SEARCH`), `label`, `description` |
| `queryExpansionPolicy` | object | `whenToBroaden`, `whenToNarrow`, `maxExpansionRounds` |
| `openUnknowns[]` | object[] | Explicit unknowns: `id`, `question` |
| `constraints[]` | object[] | Hard constraints carried from the brief: `id`, `description` |
| `discoveryLimits` | object | Guardrails for a run, matched to how the collector actually iterates (query → ads, via scrolling): `maxQueriesPerRun`, `maxAdsPerQuery`, `maxScrollsPerQuery`, `stopAfterScrollsWithoutNewAds`, `maxRuntimeMinutes` |
| `saturationCriteria[]` | object[] | "Stop for now" conditions: `id`, `description` |
| `changeSummary` | string | **Required** (schema-enforced) on every version: `""` for MR-01, non-empty for MR-02, mechanically generated by the app from a structural diff for manual revision (see [07-api-contract.md](07-api-contract.md)) — never a required free-text field the user must type |
| `warnings[]` | string[] | **Required** (schema-enforced); empty array if none |

## Stable IDs

Every `id` inside a `DiscoveryPlanV1` document (in `seedQueries`, `candidateProductTypes`,
`initialTaxonomy`, `discoveryStrategies`, `openUnknowns`, `constraints`, `saturationCriteria`)
follows the same simple rule set across a revision (MR-02 or manual):

- **Unchanged item** → same `id` as the previous version.
- **Edited item, same conceptual position/purpose** (e.g. the user tweaked a query's wording,
  or MR-02 refined a rationale) → same `id`. Editing a field is not the same as removing and
  re-adding an item.
- **New item** → a new `id`, never reused from a removed item in this or any prior version.
- **Removed item** → simply absent from the new version's array; its `id` is retired and must
  not be reused.

This is a **structural** rule, not a semantic diff — the app never tries to infer "this new
 item is basically the old item reworded" on its own. It only validates the mechanical
properties above:

1. **Duplicate IDs** — two items in the same array sharing one `id` is a validation failure.
2. **Malformed ID format** — empty string or non-string `id` is already rejected by the JSON
   Schema (`minLength: 1`); the app additionally rejects IDs containing characters that would
   break using them as a UI key (e.g. embedded newlines).
3. **ID reuse across versions** — an `id` that appeared in a previous, different-purpose item
   (i.e. the app can see the same `id` string now points at a completely different `query`/
   `label` than any prior use where it was still present) is flagged as a warning, not a hard
   failure, since this is exactly the boundary where structural checking gives way to something
   only a human can judge correctly.

This validation runs both for LLM-produced versions (MR-02) and for manual revisions, since a
buggy frontend edit is just as capable of producing a duplicate ID as an LLM is.

## Validation policy (app side)

1. n8n's `Respond to Webhook` reply is parsed as JSON by the app's HTTP client (MR-01/MR-02),
   or the app assembles a candidate document itself from the user's edits (manual revision).
2. The app validates the candidate object against `DiscoveryPlanV1.schema.json` using a runtime
   validator (Zod schema mirroring the JSON Schema, or `ajv` loading the JSON Schema directly —
   left to [codex-implementation-brief.md](codex-implementation-brief.md); either is
   acceptable as long as validation happens before persistence), plus the stable-ID structural
   checks above.
3. **On validation failure from MR-01/MR-02:** the app is allowed **exactly one** repair
   attempt — re-invoke the same n8n workflow once with an added instruction to the LLM
   describing the validation error (this repair loop lives inside the n8n workflow's
   "Auto-fixing Output Parser" equivalent, or as an explicit second Basic LLM Chain call from
   the app — decide in [08-n8n-workflows.md](08-n8n-workflows.md)). If the second attempt also
   fails validation, the app surfaces a clear error to the user and **does not** store a
   partially-valid or coerced plan. No silent retries beyond this one attempt, and no
   "best effort" partial saves.
4. **On validation failure from a manual revision:** there is no LLM to re-invoke, so there is
   no repair attempt at all — the app rejects the request with a clear error identifying which
   field/id failed validation, and nothing is persisted.
5. Only a fully schema-valid `DiscoveryPlanV1` is ever written to `DiscoveryPlanVersion.planJson`.

## Versioning rule

`DiscoveryPlanV1` documents are **immutable once created**. Every MR-01/MR-02/manual-revision
call produces a brand-new `DiscoveryPlanVersion` row (see
[05-data-model.md](05-data-model.md)); nothing ever patches an existing plan's `planJson` in
place — a manual revision is exactly as append-only as an LLM revision. Each version's actual
derivation is recorded explicitly in `DiscoveryPlanVersion.parentVersionId` (`null` for MR-01,
otherwise the versionId the revise/manual-revision call was made against) — `versionNumber` is
only a monotonically increasing creation-order counter within the project and must never be
used to infer which version a given version came from. This gives a full audit trail of how a
plan evolved and makes "what changed at each step, by what mechanism, and from which parent" all
trivially inspectable — valuable both for debugging prompt behavior and for the Data Explorer
screen.

## Schema evolution

This correction round itself is an example of the process: `discoveryLimits`,
`advertiserDiscoveryStrategies` (renamed to `discoveryStrategies`), and `seedQueries[]` items
all changed shape, and required fields (`changeSummary`, `warnings`) were added — so
`schemaVersion` moved from `"1.0"` to `"1.1"`. For any future need to change the shape again:

1. Bump `schemaVersion` (e.g. `"1.2"` for additive/backward-compatible, `"2.0"` for breaking).
2. Update `DiscoveryPlanV1.schema.json`, the n8n Structured Output Parser's schema copy in both
   workflows, and the app-side validator, together, in one change — these three copies must
   never drift.
3. Old stored versions keep their original `schemaVersion` — the app must be able to *render*
   old versions even after the schema evolves (read-side must tolerate multiple
   `schemaVersion` values; write-side always targets the current version).
